# 复习工作流

根据已有证据灵活执行，不要重复已经完成的阶段。

## 1. 维护复习状态

在整个复习过程中持续记录：

| 字段 | 可能的状态 |
|---|---|
| 当前范围 | 正在复习的章节和小节 |
| 学习状态 | `incomplete` 或 `complete` |
| 当前阶段 | `collecting`、`reviewing`、`awaiting-answer`、`diagnosing`、`consolidating` 或 `complete` |
| 问题检查点 | 当前轮次以及尚未回答的问题编号 |
| 已有证据 | 笔记、源码、命令、日志、截图和用户解释 |
| 仓库状态 | 未检查、编辑中、验证中、已暂存或已同步 |

不得自行推断课程已经学完或材料已经上传完毕，必须等待用户明确说明。

## 2. 收集材料

如果用户表示还会继续上传材料：

1. 将阶段设为 `collecting`；
2. 只确认一次已经进入材料收集状态；
3. 不开始分析、提问或仓库整理；
4. 接收后续文件时不作实质性回复；
5. 只有用户明确表示“上传完毕”后才恢复工作。

材料上传完成后，先检查当前章节所需的重要文件是否齐全。根据章节内容，可能包括：

- 学习笔记；
- 源代码；
- `package.xml`；
- `CMakeLists.txt` 或 `setup.py`；
- launch 文件；
- 配置文件；
- URDF/Xacro；
- Gazebo世界或模型；
- 实际运行输出。

在进入整理前，先指出会实质影响复习的重要缺失文件。不要要求与当前阶段无关的材料。

## 3. 构建问题阶梯

按照以下层次逐渐深入，已有证据已经证明的内容可以跳过：

1. **概念**：该机制解决什么问题？
2. **数据流**：哪个组件发布、订阅、转换、存储或执行什么？
3. **运行过程**：`spin`、回调、定时器、launch、控制器或状态发布器怎样工作？
4. **故障分析**：缺少某项依赖、TF、接口或配置时会出现什么现象？
5. **项目迁移**：怎样将该知识用于移动机器人，而不只用于课程示例？

每轮默认提出3～5个相互关联的问题。

在整轮回答完成前，保留问题的原始编号和文字。

如果用户在回答过程中插入相关疑问：

1. 先回答当前疑问；
2. 保留尚未回答的问题；
3. 明确说明之后将回到哪一轮；
4. 用户要求重新展示时，必须展示原来的问题；
5. 从第一个尚未回答的问题继续。

未经解释并获得用户同意，不得擅自用一组新问题替换尚未完成的问题。

## 4. 评价回答

对每个编号对应的回答：

- 标记为**正确**、**部分正确**或**错误**；
- 概括决定判断结果的核心表述；
- 解释背后的因果机制；
- 区分概念错误和无害的措辞不准确；
- 指出还需要什么证据才能消除不确定性。

同一个知识缺口最多进行一次针对性追问。如果用户仍然不清楚，应简要讲解缺失机制，然后改用应用题验证，而不是反复换一种说法询问同一个问题。

在用户尝试回答前，不得提前展示参考答案。

## 5. 选择最小实验

选择一个能够证伪用户当前理解的最小实验。

必须说明：

- 正在验证哪个问题；
- 需要执行的最小命令或文件修改；
- 不同解释分别对应什么预期结果；
- 用户需要返回哪部分输出。

可参考以下证据：

| 主题 | 最小验证方式 |
|---|---|
| Topic | `ros2 topic info`、`echo`、`hz`、QoS或故意阻塞的回调 |
| Service | 在 `spin` 下观察 Future 完成或请求顺序 |
| Parameter | 动态参数回调和实际状态变化 |
| TF | `tf2_echo`、坐标树、时间查询或移除一个发布器 |
| URDF/Xacro | 对比修改 `joint origin` 与 `visual origin`，或停止 `/joint_states` |
| Launch | 修改一个参数或条件并观察进程 |
| Gazebo | 检查一个传感器话题或物理交互 |
| ros2_control | 查询控制器和硬件接口，再发送一个控制命令 |
| Navigation | 单独检查一个坐标系、传感器、代价地图、规划器或控制器假设 |

一个命令足以验证的问题，不要扩展成大型项目。

## 6. 处理故障但不丢失复习进度

将故障作为章节理解证据处理：

1. 找到第一处有实际意义的错误；
2. 将现象与当前章节机制联系起来；
3. 提出范围最小的检查；
4. 验证修正结果；
5. 回到保存的问题检查点。

除非用户明确要求，不要把整场章节复习变成无关的通用调试。

## 7. 整理仓库证据

修改前先检查文件，保留用户已有风格和无关改动。

章节 README 只记录有证据支持的内容：

- 学习目标和核心机制；
- 功能包或文件结构；
- 可复现的构建与运行命令；
- 实际观察结果；
- 一个有意义的故障及原因；
- 与移动机器人项目的关系；
- 尚未掌握或验证的内容。

选择范围最小的相关检查：

- 依赖或清单验证；
- 指定功能包构建；
- 语法或模型解析；
- 一次实际启动；
- 相关 Topic、TF、控制器或接口检查；
- `git diff --check`；
- `git status --short`。

对于尚未被 Git 跟踪的章节文件，普通 `git diff` 不会显示它们。应使用：

```bash
git status --short --untracked-files=all
```

告知用户后，只暂存本章需要提交的文件，再执行：

```bash
git diff --cached --check
git diff --cached --stat
git status --short
```

确保不包含以下生成文件或本机文件：

```text
build/
install/
log/
__pycache__/
*.pyc
.vscode/
自动生成的PDF和Graphviz文件
```

不得执行 `git commit` 或 `git push`。

## 8. 准确判断闭环状态

| 状态 | 含义 |
|---|---|
| 当前轮问答完成 | 当前这批问题已经回答 |
| 章节学习未完成 | 课程还有材料尚未学习 |
| 章节复习完成 | 理解和实践证据已经充分 |
| 仓库整理完成 | README、构建和Git检查已经完成 |
| 完成闭环 | 用户自行选择提交和推送，并反馈本地与远端同步且工作区干净 |

结束时应报告：

1. 掌握度及各维度依据；
2. 已纠正的错误理解；
3. 实践实验及实际结果；
4. 仓库修改和验证结果；
5. 2～4个尚未作答的面试问题；
6. 下一项最小学习或项目迁移任务。

在看到对应证据前，不得声称已经完成全部闭环。
